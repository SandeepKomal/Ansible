UNREACHABLE: Permission denied (publickey)

One or more hosts are UNREACHABLE; the message names a user@address.

Error

fatal: [web-04]: UNREACHABLE! => {"changed": false, "msg": "Failed to connect to the host via ssh: root@10.0.1.14: Permission denied (publickey).", "unreachable": true}

Why it happens

  • ansible_user is wrong for that host (check the user in the message)
  • The private key Ansible offers is not in the user's authorized_keys
  • An inventory variable overrides -u: inventory beats the command line
  • The key file path in ansible_ssh_private_key_file does not exist

Confirm the cause

ansible-inventory --host <host>   # which ansible_user and key
ssh -i ~/.ssh/<key> <user>@<address>   # does plain SSH work?
ansible <host> -m ping -vvvv   # the exact ssh command

Fix

  1. Correct ansible_user or the key in the inventory, group_vars or host_vars
  2. Install the public key for that user on the host

Prevent it

  • Set ansible_user once in group_vars/all; avoid per-host overrides
  • Bake the deploy user and key into your base image

UNREACHABLE: Connection timed out

A host takes a long time and then fails with Connection timed out.

Error

fatal: [db-02]: UNREACHABLE! => {"changed": false, "msg": "Failed to connect to the host via ssh: ssh: connect to host 10.0.2.21 port 22: Connection timed out", "unreachable": true}

Why it happens

  • Wrong ansible_host address (a typo or an old IP)
  • A firewall or security group blocks port 22 from the control node
  • The host is down or has no route
  • SSH listens on another port (ansible_port)

Confirm the cause

ansible-inventory --host <host>
nc -vz <address> 22
ssh -v <user>@<address>

Fix

  1. Correct ansible_host or ansible_port
  2. Open port 22 from the control node's address

Prevent it

  • Use a dynamic inventory plugin for cloud hosts so addresses never go stale

REMOTE HOST IDENTIFICATION HAS CHANGED

A host that worked yesterday is UNREACHABLE with a long warning about its identification.

Error

fatal: [web-03]: UNREACHABLE! => {"changed": false, "msg": "Failed to connect to the host via ssh: @@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@\r\n@    WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!     @\r\n... Host key verification failed.", "unreachable": true}

Why it happens

  • The host was rebuilt or reinstalled and has a new SSH host key
  • A different machine now has that address
  • Someone is intercepting the connection

Confirm the cause

grep <address> ~/.ssh/known_hosts
ssh-keyscan <address>   # compare with the console's fingerprint

Fix

  1. After confirming the rebuild: ssh-keygen -R <address>, then ssh-keyscan <address> >> ~/.ssh/known_hosts

Prevent it

  • Do not set host_key_checking = False: it removes protection for every host
  • Publish host keys from your image pipeline, or use SSH certificates

Host key verification failed (new host)

A new host, or a fresh CI runner, cannot connect; SSH has never seen the host's key.

Error

fatal: [web-05]: UNREACHABLE! => {"changed": false, "msg": "Failed to connect to the host via ssh: Host key verification failed.", "unreachable": true}

Why it happens

  • The host is not in known_hosts and Ansible cannot answer SSH's yes/no prompt
  • A CI runner starts with an empty known_hosts

Confirm the cause

ssh-keygen -F <address>
ssh <user>@<address>   # SSH asks to confirm the fingerprint

Fix

  1. Add the key after checking its fingerprint: ssh-keyscan <address> >> ~/.ssh/known_hosts

Prevent it

  • In CI, write known_hosts from a stored, reviewed file instead of disabling checking

Missing sudo password

Tasks with become fail immediately on some hosts.

Error

fatal: [web-03]: FAILED! => {"msg": "Missing sudo password"}

Why it happens

  • sudo on that host requires a password for ansible_user
  • No password was given: neither -K nor ansible_become_password

Confirm the cause

ssh <user>@<address> sudo -n true   # 'a password is required'

Fix

  1. Run with -K (--ask-become-pass)
  2. Or store ansible_become_password in Vault for that group

Prevent it

  • Decide per environment: NOPASSWD sudo for a dedicated deploy user, or a vaulted become password

Failed to set permissions on the temporary files

A task with become_user set to a normal user (postgres, app) fails before running.

Error

fatal: [db-01]: FAILED! => {"msg": "Failed to set permissions on the temporary files Ansible needs to create when becoming an unprivileged user (rc: 1, err: chmod: invalid mode: 'A+user:postgres:rx:allow'\n...}). For information on working around this, see https://docs.ansible.com/ansible-core/2.18/playbook_guide/playbooks_privilege_escalation.html#risks-of-becoming-an-unprivileged-user"}

Why it happens

  • Ansible must let the target user read its temporary module file, and the host has no setfacl (acl package)
  • Pipelining is off, so a temporary file is needed at all

Confirm the cause

ansible <host> -a 'which setfacl'
ansible-config dump --only-changed

Fix

  1. Install the acl package on the host
  2. Or set pipelining = True under [ssh_connection]

Prevent it

  • Include acl in base images; never set allow_world_readable_tmpfiles

MODULE FAILURE: sudo parse error in /etc/sudoers.d

Every become task fails on a host after a sudoers change.

Error

fatal: [web-01]: FAILED! => {"changed": false, "module_stderr": ">>> /etc/sudoers.d/monitoring: syntax error near line 1 <<<\nsudo: parse error in /etc/sudoers.d/monitoring near line 1\nsudo: no valid sudoers sources found, quitting\n", "msg": "MODULE FAILURE\nSee stdout/stderr for the exact error", "rc": 1}

Why it happens

  • A file with a syntax error was written to /etc/sudoers.d; sudo refuses to run at all

Confirm the cause

Console access: visudo -c

Fix

  1. Repair the file from the console or a root session (visudo -f /etc/sudoers.d/<file>)

Prevent it

  • Always deploy sudoers with validate: visudo -cf %s

A task did not run with --tags

A run with --tags succeeds but skips a step the change needed; the app fails afterwards.

Error

TASK [Run database migrations] does not appear in the output of ansible-playbook deploy.yml --tags deploy

Why it happens

  • The task has no tag, so --tags skips it silently
  • Tags on include_tasks apply to the include only, not to the tasks inside
  • The task is tagged never

Confirm the cause

ansible-playbook <playbook> --tags <tag> --list-tasks

Fix

  1. Tag the task, or tag it always when every run needs it
  2. Use import_tasks, or apply: tags on include_tasks

Prevent it

  • Review --list-tasks for the exact tags your pipeline uses

mapping values are not allowed in this context

The playbook does not start; the error names a line and column.

Error

ERROR! We were unable to read either as JSON nor YAML, these are the errors we got from each:
JSON: Expecting value: line 1 column 1 (char 0)

Syntax Error while loading YAML.
  mapping values are not allowed in this context

Why it happens

  • A line is indented deeper than the key above it, so YAML reads it as part of a value
  • A plain value contains ': ' (quote it)

Confirm the cause

ansible-playbook <playbook> --syntax-check
cat -n <playbook>

Fix

  1. Line up the module with name: of its task, options two spaces deeper
  2. Quote values that contain ': '

Prevent it

  • Use an editor with YAML support and run yamllint and ansible-lint in CI

MODULE FAILURE / python3: not found

Gathering Facts or every task fails on a host, rc 127.

Error

"module_stdout": "/bin/sh: 1: /usr/bin/python3: not found\r\n", "msg": "The module failed to execute correctly, you probably need to set the interpreter.\nSee stdout/stderr for the exact error", "rc": 127

Why it happens

  2. Or correct ansible_python_interpreter

No package matching ... is available

Package installs fail on some hosts only.

Error

fatal: [web-02]: FAILED! => {"changed": false, "failures": ["No package apache2 available."], "msg": "Failed to install some of the specified packages", "rc": 1, "results": []}

Why it happens

  • Package names differ between OS families (apache2 vs httpd)
  • The repository is not enabled, or the cache is stale (update_cache)
  • A pinned version that the repository does not have

Confirm the cause

ansible <host> -m setup -a 'filter=ansible_os_family'
ansible <host> -a 'apt-cache policy <package>'

Fix

  1. Load per-OS names with include_vars "{{ ansible_facts['os_family'] }}.yml"
  2. Add update_cache: true, or enable the repository first

Prevent it

  • Test roles on every OS you support (Molecule in CI)

Failed to lock apt for exclusive operation

apt tasks fail with a lock or permission error.

Error

fatal: [web-01]: FAILED! => {"changed": false, "msg": "Failed to lock apt for exclusive operation: Failed to lock directory /var/lib/apt/lists/: E:Could not open lock file /var/lib/apt/lists/lock - open (13: Permission denied)"}

Why it happens

  • The task does not use become, so it runs as a normal user (Permission denied)
  • Another apt run, such as unattended-upgrades, holds the lock

Confirm the cause

ansible <host> -b -a 'fuser /var/lib/dpkg/lock-frontend'

Fix

  1. Add become: true to the task
  2. Let apt wait: lock_timeout: 600 on the apt task; never delete lock files

Prevent it

  • Use become per task that needs root; schedule unattended upgrades outside deploy windows

Unable to start service: Job for x.service failed

A service will not (re)start after a config change.

Error

  1. Fix the file (use template for .j2), its owner and its mode, then restart

Prevent it

  • Use validate: on config templates (nginx -t -c %s, visudo -cf %s)

uri: Status code was ... and not [200]

A health check after a deploy fails: 503, 404, or -1 with Connection refused.

Error

fatal: [web-01]: FAILED! => {"changed": false, ... "msg": "Status code was 503 and not [200]: HTTP Error 503: Service Unavailable", "status": 503, "url": "http://localhost:8080/healthz"}

Why it happens

  • The app is not running the new configuration yet: its restart handler runs at the end of the play
  • A step the release needs was skipped (a migration left out by --tags)
  • The release itself is broken
  • The check uses the wrong port or path

Confirm the cause

ansible <group> -m uri -a url=http://localhost:8080/healthz
ansible <group> -b -a 'systemctl status <service>'
ansible-playbook <playbook> --tags <tag> --list-tasks

Fix

  1. Add meta: flush_handlers before the check
  2. Run the skipped step (tag it), or roll back the release

Prevent it

  • Deploy with serial so a failing check stops the rollout after the first batch
